# گام ۲۳ — رندر از درخت JSON

مرجع: §32–۴۴، §103، §161–۱۶۹ · Addendum §۳۰–۳۳، §۹۶، §۱۰۰، §۱۰۲

این گام، «صفحهٔ کدنوشته» را به «صفحهٔ ساخته‌شده از داده» گره می‌زند: درختی که
در `design.page.published_tree` منتشر شده، همان چیزی است که رندر می‌شود.

## زنجیرهٔ کامل

```
design.page.published_tree (jsonb)
        │
        ├─ scanTree()      ← تجزیه: کامپوننت شناخته‌شده؟ شناسه؟ عمق؟ تعداد؟
        │                     و پیش‌اسکن: به چه داده و چه دارایی‌ای نیاز داریم؟
        ├─ data.*          ← خواندن همان چیزهایی که لازم است (نه بیشتر)
        └─ renderTree()    ← اعتبارسنجی پراپ + رندر با سازنده‌های امن HTML
```

## قطعات

| فایل | کار | تصمیم کلیدی |
| --- | --- | --- |
| `registry.ts` | `design.component` ⇒ قرارداد اجرایی | هر پراپ پیش از رندر اعتبارسنجی می‌شود؛ `style`/`class`/`on*` پذیرفته نمی‌شوند |
| `tree.ts` | تجزیه، پیش‌اسکن، رندر | گرهٔ خراب **حذف** می‌شود، نه اینکه ۵۰۰ بدهد |
| `renderers.ts` | ۳۵ رندرکنندهٔ سمنتیک | `<details>`/`<nav>`/`<figure>`/`<table>` به‌جای `div` تودرتو |
| `media.ts` | ردیف دارایی ⇒ نشانی | مسیر فایل هرگز از درخواست نمی‌آید |
| `pagedesign.ts` | پیوند صفحه و درخت | درخت منتشرشده حاکم است؛ وگرنه چیدمان پایه |
| `pages/*` | مصرف‌کننده | صفحهٔ اصلی و پروفایل کسب‌وکار |

## تصمیم‌ها و دلیلشان

1. **تجزیه‌پذیری می‌سنجد، رندرکننده اعتماد نمی‌کند.** `scanTree` شکل درخت را
   می‌سنجد و `renderTree` هر پراپ را با `props_schema` همان کامپوننت اعتبارسنجی
   می‌کند. دو لایه، چون درخت از بیرون می‌آید و لایهٔ اول می‌تواند روزی دور زده
   شود (مثلاً مسیر Admin مستقیم در DB).
2. **گرهٔ نامعتبر، حذف محلی است.** یک کامپوننت خراب، بقیهٔ صفحه را نمی‌سوزاند.
   یافته ثبت می‌شود (`registry.component_unknown` سطح `blocker`)، صفحه با
   سالم‌ها رندر می‌شود.
3. **`UNRENDERABLE` فهرست صریح است، نه سکوت.** هشت کامپوننت Registry هستند ولی
   این build رندرشان نمی‌کند (فرم‌ها، جست‌وجو، فروشگاه، نظرات) — با دلیل و
   ارجاع به گام. آزمون تضمین می‌کند هیچ کامپوننت فعالی، نه رندرکننده داشته باشد
   و نه دلیلِ مستند.
4. **بُعد تصویر اجباری است.** بدون `width`/`height` تصویر چاپ نمی‌شود. جعبهٔ
   بی‌بُعد، CLS می‌سازد و CLS بخشی از بودجهٔ عملکرد است (Addendum §۱–۱۹).
5. **نشانی‌ها از یک دروازه می‌گذرند** (`sanitizeHref`): `javascript:`/`data:`/
   `vbscript:`/`blob:`، نشانی «بی‌طرح» (`//evil`)، بک‌اسلش و نشانی با نام کاربری
   رد می‌شوند. نشانی مطلق مجاز، `rel="noopener noreferrer nofollow"` و
   `target="_blank"` می‌گیرد. چرا محافظ اینجا هست و رو به روی Spread-Sheet نیست
   ...
6. **یک `h1` در صفحه.** اولین عنوان سطح ۱ می‌ماند، بقیه به `h2` تنزل می‌کنند؛
   اگر درخت اصلاً `h1` نداشت، صفحه از دادهٔ خودش `h1` می‌گذارد.
7. **شناسهٔ لنگرها پیش از رندر ساخته می‌شود.** `navigation.toc` ممکن است بالای
   صفحه باشد ولی به عنوان‌های پایین اشاره کند؛ اگر شناسه در لحظهٔ رندر ساخته
   می‌شد، پیوندها می‌شکست.
8. **رسانه: مسیر فایل از درخواست نمی‌آید.** نشانی `/media/<uuid>` است و
   `storage_key` را سرور از پایگاه‌داده می‌خواند. پیمایش مسیر در این طراحی
   ساختاراً بسته است؛ بررسی داخل‌بودن مسیر هم لایهٔ دوم می‌ماند.
9. **`svg` درون‌خطی سرو نمی‌شود.** SVG یک سند XML است؛ با
   `Content-Disposition: attachment` ریسکش صفر می‌شود.
10. **کش Registry با عمر محدود (۳۰ ثانیه).** Registry در رندر هر گره لازم است و
    خواندنش در هر درخواست، یک رفت‌وبرگشت اضافه است؛ ولی کش بی‌مرز یعنی صفحهٔ
    تازه منتشرشده با رندرکنندهٔ قدیمی تفسیر شود. شکست بارگذاری، Registry پیشین
    را نگه می‌دارد (نه اینکه صفحه را به چیدمان پایه پرت کند).

## آنچه این گام **نکرد**

- جریان انتشار از پنل (Draft → Preview → Approval → Publish) در API هست
  (گام ۲۱)، ولی رابطش گام ۳۰ است.
- صفحات چندگانهٔ کسب‌وکار (`about`, `services`, …) گام ۲۵ است؛ اینجا فقط
  صفحهٔ اصلی و پروفایل به درخت وصل شدند.
- تصویر چندنسخه‌ای (AVIF/WebP، srcset) گام ۲۷ است.
