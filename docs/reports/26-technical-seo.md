# گام ۲۶ — سئوی فنی

مرجع: §39–۴۰، §186، §191 · Addendum §۳۹–۴۷، §۴۴–۴۶، §۸۸–۹۰، PART 102

نقشهٔ سایت، robots، llms.txt، پیوند داخلی، تشخیص صفحهٔ یتیم و وضعیت IndexNow.
همه‌جا یک اصل: **آنچه به موتور جست‌وجو می‌گوییم، با آنچه صفحه می‌گوید یکی است.**

## ⚠️ رخنهٔ امنیتی که در این گام پیدا و بسته شد

هنگام وصل‌کردن robots به تنظیمات پلتفرم، معلوم شد **هر کاربر عادیِ واردشده می‌توانست
تنظیمات سراسری پلتفرم را بنویسد.** اجرای واقعی روی پایگاه‌داده:

```sql
-- کاربر عادی؛ بدون نقش پلتفرمی؛ بدون کسب‌وکار فعال؛ نقش pv_app
update ops.setting set value = '{"hacked":true}' where key = 'platform.robots';   -- UPDATE 1
insert into ops.setting (business_id, key, value) values (null, 'attacker.key', '{}'); -- INSERT 0 1
```

| | |
| --- | --- |
| **ریشه** | سیاست `setting_business_all` شرطش را `NOT (business_id IS DISTINCT FROM current_business_id())` نوشته بود. وقتی زمینهٔ کسب‌وکار **تهی** است، ردیف‌های سراسری (`business_id` تهی) هم «برابر» می‌شوند و چون سیاست `for all` بود، خواندن و نوشتنشان باز می‌شد. |
| **اثر** | تغییر `platform.security`، `platform.robots`، `platform.rate_limit`، `platform.brand`… توسط هر ثبت‌نام‌کننده. |
| **رخنهٔ همریشهٔ دوم** | `setting_global_read` برای بی‌نام فقط `business_id is null` می‌گفت: تنظیم **سرّی** (`is_secret`) برای هر بازدیدکننده خواندنی بود. (الان تنظیم سرّی‌ای نبود؛ اولین کلید یا توکن، نشت می‌کرد.) |
| **رخنهٔ همریشهٔ سوم** | `ops.idempotency_key`: همین الگو؛ بدون زمینهٔ کسب‌وکار، کلیدها و `response` ذخیره‌شدهٔ **همهٔ کاربران** خواندنی/نوشتنی بود. (هنوز هیچ کدی از آن استفاده نمی‌کرد.) |
| **چرا هیچ آزمونی نگرفتش** | قرارداد «سیاستِ pv_app به مستأجر یا کاربر گره خورده» فقط **وجود** `current_business_id()` را در متن می‌دید، نه رفتارش در زمینهٔ تهی را. سناریوها همیشه «کاربر + کسب‌وکار» داشتند. |
| **رفع** | مهاجرت `0020`: ردیف سراسری هرگز با زمینهٔ کسب‌وکار سنجیده نمی‌شود (`business_id is not null`)؛ نوشتنِ سراسری = `platform.settings.manage`؛ تنظیم سرّی = مجوز صریح؛ کسب‌وکار = عضویت + مجوز؛ کلید ایدمپوتنسی = کنشگر. «یک سیاست = یک دستور». |
| **اثبات** | `tests/rls-null-fences.test.mjs` (۲۰ آزمون: بی‌نام، کاربر بی‌کسب‌وکار، کارمند بی‌مجوز، عضو ناظر، غیرعضوِ جاعل). **با مهاجرت حذف‌شده ۱۵ از ۲۰ می‌شکنند.** |
| **نگهبان الگو** | آزمون پوشش: هر سیاستِ `IS [NOT] DISTINCT FROM app.current_business_id()` باید «غیرتهی» یا «کنشگر» را هم بخواهد. |

یک تغییر رفتاری آگاهانه: زمینهٔ کسب‌وکار **به‌تنهایی** تنظیمات را باز نمی‌کند؛ عضویت هم لازم است
(آزمون مهاجرت‌ها به همین قرارداد درست‌تر به‌روز شد).

## نقشهٔ سایت

`/sitemap.xml` **همیشه ایندکس** است؛ بخش‌ها زیر `/sitemaps/`:

| بخش | محتوا | شرط ورود |
| --- | --- | --- |
| `pages` | صفحهٔ اصلی و مرکزها | هر مرکز فقط با عضو |
| `content-{n}` | محتوای سراسری پلتفرم | منتشرشده، عمومی، نمایه‌شدنی |
| `types` · `industries` · `locations` · `categories` | تاکسونومی | دست‌کم یک عضو (همان قاعدهٔ محتوای کم‌مایه) |
| `businesses-{n}` | پروفایل‌ها | فعال، عمومی، فرادادهٔ نمایه‌شدنی |

- **صادق:** `lastmod` فقط وقتی هست که واقعی است (بخش‌های قطعه‌قطعه ندارند).
- **هم‌سو با صفحه:** صفحه‌ای که خودش `noindex` است (فرادادهٔ دستی یا کم‌مایه) در نقشه نیست. آزمون، هر نشانی نقشه را
  در محیط تولید رندر می‌کند: ۲۰۰ و بی‌noindex.
- **قطعه:** اندازه از `seo.settings.extra.indexing.max_sitemap_urls` (داده)، سقف ۵۰٬۰۰۰ پروتکل.
- **ETag و ۳۰۴** برای نقشهٔ بدون تغییر.

**نقص قدیمی:** نقشهٔ سایتِ گام ۲۲ `listPublicBusinesses({limit: 5000})` را صدا می‌زد، ولی سقف DAL ۱۰۰ است؛
**بی‌صدا در ۱۰۰ کسب‌وکار قطع می‌شد** (اندازه‌گیری شد: درخواست ۵۰۰۰ ⇒ ۱۰۰ برگشت). علاوه بر آن، کسب‌وکارِ
`is_indexable=false` را هم می‌گذاشت.

## robots.txt

- مسیرهای بسته از `ops.setting` کلید `platform.robots` (داده، §103) + مسیرهای فنی که همیشه هستند (`/search`،
  `/*?cursor=`، `/readyz`).
- **داده، دستور تزریق نمی‌کند:** مسیرِ دارای خط‌جدید، فاصله، `#` یا بدون `/` دور ریخته می‌شود (نه اصلاح) —
  وگرنه یک مقدار می‌توانست `Allow: /secret` یا `Sitemap:` جعلی اضافه کند.
- **نقص قدیمی:** گروه‌های ربات هوش مصنوعی فقط `Allow: /` داشتند. خزنده‌ای که گروه نام‌دار دارد، گروه `*` را
  **کاملاً نادیده می‌گیرد**؛ پس پنل، API و جست‌وجو برای آن‌ها باز می‌شد. حالا هر گروه فهرست ممنوعه را تکرار می‌کند.
- سیاست هوش مصنوعی سه‌حالته (`allow` · `search-only` · `disallow`) از `seo.settings` می‌آید؛ «فقط جست‌وجو»
  یعنی خزندهٔ **آموزش** بسته، خزندهٔ پاسخ‌دهی باز.

## پیوند داخلی و صفحهٔ یتیم

**پیوند داخلی**: پروفایل حالا بالا (نوع، صنف، شهر) و کناره (کسب‌وکارهای مشابه) را می‌بیند؛ پیوندهای دستیِ
سراسری (`seo.internal_link`) روی هر صفحه نمایش داده می‌شوند — فقط مسیر داخلی، چون مقدار پایگاه‌داده اعتماد نمی‌شود.

**چرخهٔ همسایه‌ها**: «n نفر بعدی به ترتیب شناسه، و از اول». هر پروفایل دقیقاً از ۶ پروفایل قبلی‌اش پیوند
می‌گیرد: **قطعی، بی‌یتیم، بی‌تصادف، با هزینهٔ O(limit)** (ایندکس). نسخهٔ نخست با `md5` می‌چرخاند و پوشش
احتمالاتی بود (آزمون در حدود ۲٪ اجراها می‌شکست)؛ آنچه می‌شود تضمین کرد، قطعی است.

**تشخیص یتیم با خزش، نه بازتولید قاعده**: گراف پیوند حاصل رندر است. بازتولیدش در SQL دو منبع حقیقت می‌ساخت.
`/sitemap.xml` را مثل یک خزندهٔ واقعی باز می‌کند، هر صفحه را رندر می‌کند و پیوندها را به **ناحیه** می‌شکند:
سرصفحه، پاورقی، مسیر راهنما، بدنه. پیوندِ سرصفحه/پاورقی در هر صفحه هست، پس هیچ‌چیز نمی‌گوید؛ «پیوند ورودی»
فقط بدنه یا مسیر راهنما از صفحهٔ دیگر است.

```bash
npm run seo:crawl            # گزارش
npm run seo:crawl -- --write # ثبت در seo.content_opportunity (ایدمپوتنت، خودبسته‌شونده)
```

کد خروج ۱ = پیوند شکسته یا نشانیِ ناسالم در نقشه («انتشار نکن»)؛ یتیم هشدار است. ثبت: یکتایی جزئی برای
فرصت‌های باز (مهاجرت `0021`)، بستن خودکار فقط برای `open` (کارِ آدمی، `planned`/`in_progress`، دست‌نخورده)، و
برای کسب‌وکارِ یتیم، سه هم‌نوع پیشنهادی.

## IndexNow (PART 102: وضعیت صریح)

`seo.indexnow` در تنظیمات غیرسرّی؛ `/{کلید}.txt` فقط وقتی ۲۰۰ می‌شود که کلید تنظیم شده، معتبر و برابر مسیر
باشد؛ هر حالت دیگر همان ۴۰۴ همیشگی (اوراکل نمی‌سازد). کلید ساختگی ساخته نمی‌شود: «تنظیم‌نشده» وضعیتی صادقانه
است. **ارسال** نشانی‌ها کار کارگر است (گام ۳۲) با آداپتور گام ۲۰.
