# ADR-0011 — نوشتن‌های ممتاز: تابع دامنه، نه گرنت تازه و نه حذف `returning`

- **تاریخ:** ۲۰۲۶-۱۰-۰۲
- **وضعیت:** پذیرفته
- **مرجع:** §14، §17، §48–۶۳، §93–۹۹؛ Addendum §21–۲۴، §56–۷۲، §99؛ ROADMAP گام ۱۹

## زمینه

در گام ۱۹ (Repositoryها) سه بار به یک دیوار خوردیم — هر بار با یک چهرهٔ متفاوت:

1. **`ops.enqueue` ⇒ `42501`.** جدول `ops.job` هیچ گرنت درج برای `pv_app` ندارد؛
   فقط `pv_worker`. طراحی درست بود، مسیر نوشتن غلط.
2. **`identity.create` ⇒ RLS.** درج انجام می‌شد ولی `insert … returning` رد
   می‌شد: `returning` یک **خواندن** است و سیاست خواندن `auth.app_user` ردیف
   غریبه را نمی‌دهد — و در ثبت‌نام، کاربر هنوز «کسی» نیست.
3. **`recordSecurityEvent` ⇒ RLS.** همان الگو: نویسندهٔ رخداد امنیتی ممکن است
   کاربر بی‌نام باشد، ولی خواندن رخداد فقط حق کارکنان پلتفرم است.

هر سه، یک سؤال مشترک داشتند: **وقتی کسی باید بنویسد ولی اجازهٔ خواندن نتیجه را
ندارد، چه کنیم؟**

## تصمیم

**مسیر نوشتن‌های ممتاز، تابع دامنهٔ `security definer` است** — با سه شرط
غیرقابل‌مذاکره:

1. تابع، **مجوز یا وضعیت زمینه را خودش می‌سنجد** (`app.has_permission`،
   `app.current_user_id()`، `app.current_platform_role()`).
2. تابع، **بازیگر را از زمینه می‌گیرد، نه از پارامتر**. اگر فراخوان می‌توانست
   «فاعل» را تعیین کند، مهاجم رد پای خود را به دیگری می‌انداخت.
3. گرنت `execute` صریح و بسته است؛ `revoke all … from public` اول می‌آید.

نمونه‌ها: `ops.enqueue_job` (کار)، `app.register_user` (ثبت‌نام)،
`app.transition_content`/`app.schedule_content` (وضعیت)، `app.accept_invitation`.

### چه چیزی را رد می‌کنیم

- **گرنت تازه به نقش برنامه** — گرنت درج روی جدول صف یعنی هر مسیر کدی می‌تواند
  کار بسازد، بی‌گذر از سنجش مجوز. گرنت، تصمیمِ یک‌بارهٔ اسکیماست؛ سنجش مجوز،
  تصمیمِ هر فراخوانی.
- **حذف سیاست RLS** — سوراخ‌کردن حصار، برای همیشه.
- **`returning` با دور زدن** — اگر نویسنده حق خواندن ندارد، پاسخ درست «ردیف را
  نگیر» است، نه «اجازهٔ خواندن بده». پس `recordSecurityEvent` بدون `returning`
  کار می‌کند و تأیید ثبت برمی‌گرداند.

## پیامدها

- سه مهاجرت تازه (`0012`, `0013`, `0014`)، هیچ‌کدام «گشادکردن دسترسی» نیست.
- API همیشه یک نقطهٔ سنجش دارد: «این کار مجاز است؟» — و پاسخ در SQL است، نه در
  کد فراخوان. کارگر و API، یک تصمیم می‌گیرند.
- هزینه: نوشتن‌های ممتاز، SQL بیشتری می‌خواهند. فایده: یک گرنت اشتباه، دیگر
  به نشت تبدیل نمی‌شود.

## تصمیم‌های همراه

- **`mapDatabaseError` گشاد شد** (`55000 ⇒ precondition_failed`، `22xxx ⇒
  validation_failed`، `23P01 ⇒ conflict`): خطای دامنه نباید به «خطای داخلی»
  تبدیل شود؛ کاربر باید بداند «وضعیت اجازه نمی‌دهد»، نه «مشکل فنی».
- **`asRole` خطای `reset role` را می‌پوشاند**: در تراکنش لغوشده، خطای دوم
  خطای اصلی را بی‌اثر می‌کرد؛ بازگشت تراکنش نقش را برمی‌گرداند.
- **فهرست بستهٔ عملگرهای شرط، آینهٔ `case` تابع SQL است** — نه فهرستی از
  تصور. عملگری که در SQL نیست، قاعده‌ای می‌سازد که بی‌صدا هرگز تطبیق نمی‌خورد.
