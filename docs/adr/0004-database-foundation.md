# ADR-0004 — بنیان پایگاه‌داده: موتور محلی، نقش‌ها، و سیاست‌ها

- **تاریخ:** ۲۰۲۶-۱۰-۰۲
- **وضعیت:** پذیرفته‌شده
- **مرجع:** §48–§63، §14، §24، §57، §93–۹۴، §106، §146–۱۵۱؛ Addendum §۲۱–۲۴

## ۱. موتور محلی: PostgreSQL تعبیه‌شده، نه شبیه‌سازی

سرور PostgreSQL روی این محیط نصب نیست. به‌جای جایگزین‌سازی با یک لایهٔ ساختگی،
از PGlite استفاده می‌شود: **همان PostgreSQL نسخهٔ ۱۸**، کامپایل‌شده به
WebAssembly و اجراشده درون فرایند.

چرا این تفاوت مهم است: RLS، تریگرها، قیدها، `for update skip locked` و توابع
دامنه همه واقعی‌اند. پس آزمون «کارگر موازی، یک کار را دو بار برنمی‌دارد» یا
«کسب‌وکار الف، ردیف کسب‌وکار ب را نمی‌بیند» واقعاً سنجیده می‌شود، نه اینکه شبیه
سازی شود. منبع حقیقت همیشه فایل‌های SQL در مخزن است و روی هر PostgreSQL —
از جمله میزبانی‌شده — بدون تغییر اجرا می‌شوند (§49–۵۱).

**محدودیت صریح:** افزونه‌های بیرونی (`pg_trgm`، `unaccent`، `pgcrypto`،
`ltree`، `fuzzystrmatch`، `postgis`) در نسخهٔ تعبیه‌شده نیستند. پس مهاجرت‌ها به
هیچ افزونه‌ای وابسته نمی‌شوند. یک تست، نبود افزونهٔ ناخواسته را تضمین می‌کند.
جست‌وجوی متنی با `tsvector` و ستون نرمال‌شدهٔ خودمان انجام می‌شود و جست‌وجوی
پیشرفته از راه آداپتور می‌آید (Addendum §۳۶–۵۵).

## ۲. چهار نقش اجرا، بدون نقش «همه‌کاره»

| نقش | کاربرد | اختیار |
| --- | --- | --- |
| `pv_app` | فرایند API درخواست‌های کاربر تأییدشده | تنها با زمینهٔ کسب‌وکار/کاربر؛ تحت RLS |
| `pv_public` | درخواست بی‌نام | فقط دادهٔ عمومی و منتشرشده |
| `pv_worker` | کارگر صف و کارهای زمان‌بندی‌شده | صف، رخداد، حسابرسی |
| `pv_reader` | گزارش و پشتیبان | فقط خواندن |

نقش مهاجرت/seed، مالک جدول‌هاست و هیچ‌وقت نقش اجرای برنامه نیست.

## ۳. RLS روشن، بدون `force` — با نگهبان در زمان راه‌اندازی

`force row level security` مالک جدول را هم به سیاست‌ها می‌بَرد؛ در نتیجه نقش
مهاجرت و seed نمی‌تواند دادهٔ مرجع بنویسد و تعمیر داده ناممکن می‌شود. پس فقط
`enable` می‌شود و خطر واقعی — «برنامه اشتباهی با نقش مالک وصل شود» — با یک
نگهبان برطرف می‌شود:

```sql
select app.rls_is_enforced_for_current_user();
```

اگر این تابع برای اتصال جاری `false` بدهد، یعنی نقش جاری مالک جدول‌های دارای
RLS است و سیاست‌ها روی آن اثر ندارند. برنامهٔ API در زمان راه‌اندازی این را
بررسی می‌کند و بالا نمی‌آید. سیاستِ نوشته‌شده با سیاستِ اعمال‌شده یکی نیست؛
این تفاوت را اندازه می‌گیریم، نه فرض.

## ۴. جدول‌های افزودنی، واقعاً افزودنی

`ops.audit_log` و `ops.event` تریگر دارند که هر `update` یا `delete` را رد
می‌کند — برای همهٔ نقش‌ها، از جمله مالک. اختیار `update`/`delete` هم از نقش‌های
اجرایی گرفته شده است. «غیرقابل‌ویرایش» یک ادعای مستند نیست؛ یک قید آزمون‌پذیر
است (§94).

## ۵. صف در پایگاه‌داده، با `for update skip locked`

چند کارگر می‌توانند موازی از یک صف بردارند بدون اینکه یک کار دو بار اجرا شود
و بدون نیاز به سرویس صف بیرونی. کلید `dedupe_key` هم می‌گذارد کار یکسان، دو
بار در صف ننشیند (§180).

## پیامدها

- محیط توسعه بدون نصب هیچ سرویسی کار می‌کند.
- مهاجرت‌ها قابل حمل‌اند: نه افزونه، نه وابستگی به میزبان (§184–۱۸۵).
- اجرای تولید باید با نقش غیرمالک انجام شود؛ این الزام در Runbook و در پروفایل
  سلامت سیستم بررسی می‌شود.
